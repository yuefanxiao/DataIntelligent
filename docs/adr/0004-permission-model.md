# 权限模型：双表面默认拒绝 + 表级 FQN 白名单授权 + key→用户

v1 网关权限 = **双表面**：业务数据面（`execute_sql`）默认拒绝、白名单授权；语义元数据面（五个只读语义工具）认证即读。授权统一挂**表 FQN**（`服务.库.表`，与本体 Table 实体同一命名空间），指标/概念授权编译期展开为表授权；凭据 = opaque 随机串（`dgw_` 前缀）哈希存储、key 绑定用户、扁平 grants、一用户多 key；grants YAML + CLI 维护，编译进语义存储 PG 权限表；PG 侧一个共享只读角色只保「物理不能写」。来源：票据 03（issue #4），2026-08-11 拍板。

## Considered Options

- **默认策略：业务面默认拒绝 vs 默认放行+黑名单**：生产数据只读也有泄露成本，网关的存在意义就是显式授权；白名单下「新表/未知表」天然无权限。→ 默认拒绝；语义元数据面单独开卷（只读独立语义存储，不触业务数据，开卷才能支撑「发现→解析→执行」工作流）。
- **粒度：表级 vs 列级拒绝/掩码 vs 行级 RLS**：掩码需改写结果集、join 语义复杂；RLS 需主→从复制角色映射、v1 无多租户诉求。→ v1 仅表级；列级/行级/掩码后置为后续优化（12 排期）。
- **挂载点：语义实体 vs 物理表**：本体就是物理拓扑模型（服务↔库↔表↔列），两者同一命名空间，不存在两套授权面；指标/概念授权在编译期展开为底层表授权，执行侧只查表级，杜绝「指标有权但底层没权」的悬空。→ 表 FQN 挂载 + 编译期展开。
- **主体：key→用户直挂 vs RBAC 角色 vs key 自带 scope**：消费方是几位开发人员，角色中间层徒增维护面；用户身份稳定是审计「谁查了什么」的聚合维度。→ key→用户扁平 grants，数据结构留 `role` 字段。
- **凭据：opaque 随机串哈希 vs JWT**：吊销必须查库，JWT 的无状态自校验是减分项（吊销时仍要查库，不如直接查哈希）。→ opaque + sha256 哈希，明文仅创建时打印一次。
- **维护方：YAML+CLI vs 管理工作台**：与语义层作者入口同构（07 已定 YAML + 同步管线），Git review 即权限变更评审闸门；控制台是 v2 候选。→ grants YAML + CLI；授权数据编译进语义存储 PG 权限表，网关启动加载内存 + 热重载。
- **通配授权：服务/库级通配编译期展开 vs `*` 全库**：展开=快照，新表默认拒绝 + 管线「未覆盖表」告警 + 改 grants YAML 触发重展开（新表永远被动放行）；`*` 不开放——「全授权」应是显式写出的少数情况。→ 服务/库级通配语法糖，编译期展开为具体表清单。
- **PG 侧分工：一个共享只读角色 vs per-service 账号**：几十个服务拆账号是运维负担、且细粒度全在网关侧，账号隔离是重复防御。→ 共享只读角色（只读强制 + `statement_timeout` + 禁 `SET ROLE`/临时表 + 行数兜底）；角色风暴不进 PG。
- **SQL 解析失败行为：拒绝 vs 放行兜底**：默认拒绝哲学下没有「解析不了就放行」的漏洞面；表不在本体 = 无授权 = 拒绝。→ 一律拒绝，错误信息区分「语法错误」vs「无权限表」。
- **管理边界：无管理员角色 vs 管理员口令**：CLI 仅网关宿主机可运行（能上宿主机 = 运维者）；管理口令随 v2 控制台。→ v1 无管理员角色。

## Consequences

- `execute_sql` 网关侧必经 SQL 解析（pg_query 提取引用表）逐表比对授权；解析器供 10 的 dry-run 校验复用。
- 授权数据存语义存储 PG 权限表；新表默认拒绝 + 管线告警（告警流程归 08 细化）；指标/概念授权展开随同步管线重算。
- key→用户身份是 04 审计的聚合维度（用户维度聚合、key 为设备维度）；`plan_id` 溯源口子不变。
- 语义元数据面开卷：全部合法 key 可读——敏感信息不进入语义层 YAML 面（由业务面表级授权兜底）。
- 列级权限、行级 RLS、掩码、key 过期策略、管理工作台 = 后续优化 / v2（12 阶段切分时排期）。
