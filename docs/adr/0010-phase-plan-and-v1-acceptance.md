## Considered Options

- **执行序：先建后写 spec vs 先 spec 后建 vs 只产 spec**：先 spec 后建 = spec 无实物经验背书、评审只能评纸面；只产 spec = v1「做出来」与「先在本地跑起来验证」（Q11c、Notes 已定）落空；先建 v1 再写 spec = spec 从真实构建经验长出、评审面对跑起来的实物（demo 重放验收用例）、构建暴露的问题在 spec 内化。→ **v1 构建先行**（地图内执行，task 票 14）。
- **v1 覆盖：试点子集 vs 全部服务**：试点（如支付链路）= 语义人工确认成本可控，但「最小完整闭环」与采集器/同步管线/权限的规模化验证都要等阶段 2，v1 交付即返工一半；全部服务（~/cloud/neo-cloud 13 服务/10 库）= 一次到位，验收用例矩阵兼证全量声明，语义人工确认（13 服务分批）是 v1 构建票的 HITL 大头。→ **全部服务**（用户拍板）。
- **语义完成度：按确认进度 vs 全服务人工确认**：按确认进度 = 未确认表走 05 原料路径回退，v1 验收只需支付域完整；全服务确认 = 结构 + 语义（指标/概念/枚举）13 服务全量人工确认，验收用例每服务可做深。→ **全服务**（与 v1 覆盖一致的完整度声明）。
- **验收用例：单主用例 vs 用例矩阵**：单主用例（支付失败率）= 演示充分但证伪不了「全服务」与校验层硬路径（多表 join/窗口函数/子查询的 AST 分类与授权展开）；用例矩阵 = 每服务 ≥2 简单 + ≥1 复杂（核心链路多表 join + 聚合 + 时间窗口）+ 主用例 + 负向/边界 5 例（无 grants 测试用户），兼作 08 golden 语料。→ **用例矩阵**（约 40+ 用例，半自动化重放，判定三件套，v1 后按效果迭代）。
- **评审门禁：一次全量 vs 逐阶段全量 vs 一次全量 + 入口轻量**：逐阶段全量 = 评审成本线性膨胀；一次全量（spec + demo）+ 阶段入口轻量评审（一句话确认 + 变更记录）= 关键路径（spec 与 v1 验收）重投入、后续阶段只核对增量。→ **一次全量 + 阶段入口轻量**。
- **阶段划分轴：覆盖/能力/开放 vs 运营化/能力/工作台**：v1 吃下全服务覆盖后，「覆盖扩展」轴作废，剩余工作按 运营化（采集保鲜自动化 + 监控 + 生产通路）→ 能力深化（规划引擎/权限优化/工作台管理面）→ 工作台 + 开放（内置 Agent 界面、PM 接入）三段切。→ **运营化 / 能力深化 / 工作台+开放**，里程碑制无日历日期。
- **PM 查询消费：Out of scope vs 阶段 4**：原决议「PM 自助 Web 查询界面」出目的地（v1 消费方 = 开发人员）；终点形态澄清后，PM 经工作台 Agent 界面查询是阶段 4 交付物，目的地范围相应扩展（v1 消费方不变）。→ **移入阶段 4**（Out of scope 条目删除，fog「管理工作台」并入）。
- **负载防护数值**（机制 10 已定）：每 key 并发 2 / 进程级 8 / statement_timeout 30s（可配）——单机网关 + 从库 + 13 服务团队规模下压住「大量长查询」速率攻击又不过度约束开发使用；SQL 限额 500/5000 确认（02 已定）。→ **按上述数值**，写 spec 参数表、env 可覆盖。
